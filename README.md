# Invoice Keeper — бэкенд

Система напоминаний о регулярных платежах: аренда, подписки, серверы.
Администратор вносит платежи, система напоминает в Telegram минимум за 3 дня до срока,
команда отмечает оплату и видит, что просрочено.

**Стек:** Python 3.11+ · FastAPI · MySQL 8.0 (готовая схема из `db/invoice_keeper_db.sql`) · Uvicorn.
Внешних очередей и брокеров нет: фоновый планировщик живёт внутри приложения.

---

## 1. Как устроен проект

Запрос от клиента принимает **API** (`app/main.py`), проверяет права и вызывает нужный метод
**бэкенда**; бэкенд работает с MySQL и возвращает результат, API отдаёт его клиенту.

```
клиент  ->  app/main.py (API, FastAPI)
                 |  проверка авторизации и роли — app/security.py
                 v
            app/services.py (бизнес-логика: платежи, периоды, итоги, пользователи)
                 |
                 v
            app/database.py (пул соединений MySQL)  ->  MySQL
                 ^
            app/reminders.py (планировщик и Telegram-бот)
```

| Файл | За что отвечает |
|---|---|
| `app/main.py` | **API.** Все адреса `/api/v1/...`, проверка прав, коды ответов, Swagger. Бизнес-логики нет. |
| `app/services.py` | **Бэкенд.** Регулярные платежи, периоды, просрочка, итоги, пользователи, бюджеты, демо-дата. |
| `app/security.py` | Пароли (bcrypt), сессии, роли, журнал действий, администратор из `.env`. |
| `app/database.py` | Пул соединений MySQL и единственное место, где выполняются SQL-запросы. |
| `app/reminders.py` | Планировщик: достраивает периоды, шлёт напоминания в Telegram, принимает кнопку «Оплачено». |
| `app/schemas.py` | Схемы запросов и ответов (валидация входных данных). |
| `app/config.py` | Чтение настроек из `.env`. |
| `db/invoice_keeper_db.sql` | Готовая база: таблицы, представления, триггеры, тестовые данные. |

Бизнес-правила кейса реализованы **совместно с базой**: представление
`v_payment_occurrences_detailed` считает просрочку и признак «нужно напомнить»,
триггеры не дают изменить плановый срок и чистят дату при снятии отметки,
а приложение отвечает за генерацию периодов и права доступа.

## 2. Быстрый старт через Docker (рекомендуется)

Нужен только Docker. MySQL поднимется сам и импортирует дамп при первом запуске.

```bash
cp .env.example .env          # Windows: copy .env.example .env
# в .env задайте ADMIN_PASSWORD (и Telegram, если нужны напоминания)
docker compose up --build
```

* Swagger: <http://localhost:8000/api/v1/docs>
* Проверка: <http://localhost:8000/api/v1/health>
* MySQL снаружи доступна на порту `3307` (чтобы не конфликтовать с локальной).

Остановить: `docker compose down`. Полный сброс вместе с данными: `docker compose down -v`.

## 3. Запуск без Docker

### 3.1. Импорт базы

Требуется MySQL 8.0.16+ (нужны `CHECK`-ограничения). Импорт выполняется **от root**: в дампе
есть `SET GLOBAL log_bin_trust_function_creators = 1`, для этого нужны права администратора.

```bash
mysql -u root -p < db/invoice_keeper_db.sql
```

Отдельный пользователь для приложения (по желанию, но так правильнее):

```sql
CREATE USER 'invoice_keeper'@'localhost' IDENTIFIED BY 'ваш_пароль';
GRANT SELECT, INSERT, UPDATE, DELETE ON invoice_keeper.* TO 'invoice_keeper'@'localhost';
FLUSH PRIVILEGES;
```

### 3.2. Настройки

```bash
cp .env.example .env
```

Заполните `DB_PASSWORD` и `ADMIN_PASSWORD`. Остальное можно оставить по умолчанию.

### 3.3. Запуск

**Windows:** двойной щелчок по `run.bat` — он создаст окружение, поставит зависимости,
прогонит тесты, выгрузит спецификацию и запустит сервер.

**Linux / macOS:** `./run.sh`

**Вручную:**

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 4. Переменные `.env`

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | Подключение к MySQL | `127.0.0.1:3306`, база `invoice_keeper` |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_FULL_NAME` | Учётная запись администратора. **Только здесь**: через API её не изменить и не удалить | `admin` |
| `SESSION_TTL_HOURS` | Сколько живёт сессия | `24` |
| `SESSION_COOKIE_NAME`, `SESSION_COOKIE_SECURE` | Имя cookie и режим HTTPS | `invoice_keeper_session`, `false` |
| `APP_TIMEZONE` | Единый часовой пояс приложения и базы | `Europe/Moscow` |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | Бот и чат для напоминаний | пусто (напоминания выключены) |
| `TELEGRAM_PAID_BUTTON` | Кнопка «Оплачено» в сообщении бота | `true` |
| `SCHEDULER_ENABLED`, `SCHEDULER_INTERVAL_SECONDS` | Фоновая проверка сроков | `true`, `60` |
| `DEFAULT_REMIND_DAYS_BEFORE` | За сколько дней напоминать | `3` (минимум по условию кейса) |
| `CORS_ORIGINS` | Адреса веб-панели через запятую | `*` |

Приложение запускается и без Telegram: периоды создаются, API работает,
в журнал пишется предупреждение, что напоминания отключены.

## 5. Telegram

1. В [@BotFather](https://t.me/BotFather): `/newbot` → получите токен.
2. Добавьте бота в чат команды и напишите там любое сообщение
   (в группе — `/start@имя_бота`).
3. Узнайте `chat_id`: откройте
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найдите `"chat":{"id":...}`
   (у групп он отрицательный).
4. Впишите `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `.env` и перезапустите приложение.

Напоминание приходит с названием, суммой, валютой и датой оплаты, а под сообщением —
кнопка **«✅ Оплачено»**: нажатие отмечает период оплаченным прямо из чата.

## 6. Роли и доступ

| Действие | Администратор | Пользователь |
|---|:---:|:---:|
| Видеть платежи, периоды, итоги | да | да |
| Отмечать и отменять оплату, исправлять фактическую дату | да | да |
| Создавать и прекращать регулярные платежи | да | **нет (403)** |
| Создавать, менять и удалять пользователей | да | **нет (403)** |
| Журнал действий, бюджеты, демо-дата | да | **нет (403)** |

Ограничения проверяются в API, поэтому действуют и в веб-панели, и при прямом обращении к API.
Учётная запись администратора задаётся в `.env`; при старте она синхронизируется в таблицу
`users` с флагом `is_env_admin`, и любые попытки изменить или удалить её через API получают 403.

**Авторизация.** `POST /api/v1/auth/login` возвращает токен и ставит HttpOnly-cookie.
Дальше подойдёт любой из способов: cookie (браузер шлёт сам) или заголовок
`Authorization: Bearer <токен>`. Без авторизации любой адрес с данными отвечает 401.

## 8. Сценарий демонстрации

Полный путь из ТЗ — от добавления платежа до следующего периода.

**1. Войти администратором**

```bash
curl -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"ВАШ_ПАРОЛЬ"}'
```

Скопируйте `access_token` — дальше он подставляется в заголовок `Authorization`.

**2. Добавить регулярный платёж** (срок через 2 дня — напоминание уйдёт сразу)

```bash
curl -X POST http://localhost:8000/api/v1/recurring-payments \
  -H "Authorization: Bearer ТОКЕН" -H "Content-Type: application/json" \
  -d '{"name":"Аренда офиса","amount":90000.00,"currency":"RUB","start_date":"2026-10-26"}'
```

**3. Получить напоминание в Telegram** — планировщик проверяет сроки раз в минуту.
Не ждать: `POST /api/v1/reminders/run`.

**4. Войти пользователем и отметить оплату**

```bash
curl -X PATCH http://localhost:8000/api/v1/payment-occurrences/1 \
  -H "Authorization: Bearer ТОКЕН_ПОЛЬЗОВАТЕЛЯ" -H "Content-Type: application/json" \
  -d '{"is_paid": true}'
```

**5. Показать просроченный платёж** — в тестовых данных это «Выделенные серверы Aéza Cloud»
(срок 3 дня назад):

```bash
curl "http://localhost:8000/api/v1/payment-occurrences?overdue=true" -H "Authorization: Bearer ТОКЕН"
```

**6. Исправить фактическую дату оплаты** — просрочка пересчитается, плановый срок не изменится:

```bash
curl -X PATCH http://localhost:8000/api/v1/payment-occurrences/4 \
  -H "Authorization: Bearer ТОКЕН" -H "Content-Type: application/json" \
  -d '{"is_paid": true, "actual_payment_date": "2026-10-21"}'
```

**7. Показать следующий период с отдельным статусом**

```bash
curl "http://localhost:8000/api/v1/payment-occurrences?recurring_payment_id=2" -H "Authorization: Bearer ТОКЕН"
```

### Сдвиг «сегодня» для показа без ожидания

```bash
curl -X PATCH http://localhost:8000/api/v1/settings \
  -H "Authorization: Bearer ТОКЕН" -H "Content-Type: application/json" \
  -d '{"override_today": "2026-12-01"}'
```

Просрочка и напоминания пересчитываются сразу. Возврат к реальной дате: `{"override_today": null}`.

## 9. Проверка решения

**Тесты бизнес-логики** — база не нужна, правила проверяются на SQLite-двойнике схемы:

```bash
python -m unittest discover -s tests -t .
```

Покрыто: якорный день (31 янв → 28 фев → 31 мар), просрочка и её пересчёт, отметка и отмена
оплаты, неизменность планового срока, следующий период при просрочке предыдущего, напоминания
без дублей, прекращение платежа с сохранением истории, итоги по трём валютам, права ролей,
состав эндпоинтов из ТЗ.

**Сквозная проверка живого API** (сервер уже запущен, MySQL настоящая):

```bash
python scripts/smoke_api.py
```

Скрипт проходит весь сценарий защиты и печатает результат по шагам.

## 10. Как выполнены требования кейса

| Требование | Решение |
|---|---|
| Напоминание минимум за 3 дня, без дублей | Планировщик раз в минуту; условие в представлении базы; перед отправкой период «бронируется» одним `UPDATE ... WHERE reminded_at IS NULL`, поэтому второе сообщение невозможно |
| Платёж добавили позже, чем за 3 дня | Период создаётся сразу при создании платежа и попадает в ближайшую проверку |
| Нет такого числа в месяце | День берётся из якоря шаблона и обрезается до последнего дня месяца: 31 янв → 28 фев → **31** мар |
| Просрочка | Считается динамически: не оплачен и срок прошёл, либо оплачен позже срока. Оплата в день срока — вовремя |
| Исправление фактической даты | Пересчитывает просрочку; плановый срок защищён и в коде, и триггером базы |
| Новый период не стирает прошлые | Каждый период — отдельная строка со своим статусом; следующий создаётся независимо от просрочки |
| Удаление регулярного платежа | Мягкое: `is_deleted = TRUE`. Новых периодов и напоминаний нет, история оплат остаётся |
| Три валюты | RUB, USD, EUR; итоги считаются отдельно по каждой, без конвертации. В ответе всегда три строки |
| Две роли | Администратор из `.env` (через API не изменяется), пользователи — в базе. Ограничения проверяются в API |
| Данные переживают перезапуск | Всё в MySQL, включая сессии: после перезапуска вход сохраняется |
| Документация | Swagger `/api/v1/docs` + файлы `openapi.yaml` и `openapi.json` |

## 11. Если что-то не работает

| Симптом | Что делать |
|---|---|
| `MySQL недоступен на 127.0.0.1:3306` | Запущен ли сервер MySQL; проверьте `DB_HOST` и `DB_PORT` в `.env` |
| `MySQL отказал в доступе` | Неверные `DB_USER` / `DB_PASSWORD` |
| `В базе не хватает объектов` | Дамп импортирован не полностью. Повторите `mysql -u root -p < db/invoice_keeper_db.sql` (целиком, вместе с блоками `DELIMITER`) |
| `Функция fn_today() недоступна` | Импорт выполнялся без прав на создание функций — импортируйте от `root` |
| Напоминания не приходят | Пусты `TELEGRAM_BOT_TOKEN` или `TELEGRAM_CHAT_ID`; бот не добавлен в чат; проверьте `POST /api/v1/reminders/run` и журнал приложения |
| 401 на всех запросах | Истёк токен — войдите заново (`SESSION_TTL_HOURS`) |
| 403 у администратора | Вход выполнен под обычным пользователем: проверьте `GET /api/v1/auth/me` |
