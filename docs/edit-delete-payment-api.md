# Изменение и удаление регулярного платежа — инструкция к API

Оба действия доступны **только администратору**. Пользователь получит **403**.
Авторизация как обычно: cookie после входа или заголовок `Authorization: Bearer <токен>`.

---

## Главное правило: история не переписывается

Каждый платёж (шаблон) порождает периоды — конкретные счета на конкретные даты.
При изменении платежа периоды делятся на две группы:

| Группа | Что это | Что с ней происходит при изменении |
|---|---|---|
| **История** | Оплаченные периоды и неоплаченные со сроком **раньше сегодня** (просроченные) | Не меняется: сумма, валюта, дата, кто оплатил — всё остаётся как было |
| **Будущие** | Неоплаченные периоды со сроком **сегодня или позже** | Получают новую сумму/валюту или пересоздаются по новому графику |

«Сегодня» — это дата системы, с учётом демо-сдвига из `PATCH /api/v1/settings`.

---

## 1. PATCH `/api/v1/recurring-payments/{payment_id}` — изменить платёж

**Передавайте только то, что меняете.** Можно прислать и форму целиком — поля, значения
которых не изменились, ни на что не повлияют.

### Тело запроса — все поля необязательные, но нужно хотя бы одно

| Поле | Тип | Правила | Что произойдёт |
|---|---|---|---|
| `name` | string | 1–255 символов, не пустое | Новое название сразу видно везде, включая историю |
| `amount` | number | > 0, максимум 2 знака после запятой | Новая сумма у шаблона и у будущих периодов |
| `currency` | string | `"RUB"`, `"USD"`, `"EUR"` | Новая валюта у шаблона и у будущих периодов |
| `start_date` | string `YYYY-MM-DD` | 2000–2100 | **Смена графика**: дата ближайшей оплаты. Будущие периоды пересоздаются от неё |
| `anchor_day` | int | 1–31 | **Смена графика**: день месяца для периодов. Нет такого числа в месяце — последний день |
| `remind_days_before` | int | 3–60 | За сколько дней слать напоминание. Действует сразу |
| `periodicity` | string | только `"monthly"` | Сейчас единственный вариант |

Передать `null` в любое поле нельзя → **422**. Неизвестное поле (например `is_deleted`) → **422**.

### Подробно о каждом виде изменения

**Название и напоминание** (`name`, `remind_days_before`) — меняется только шаблон, периоды не трогаются.
Если увеличить `remind_days_before` и будущий период попал в новое окно — напоминание уйдёт
при ближайшей проверке планировщика.

**Сумма и валюта** (`amount`, `currency`) — меняются у шаблона и у будущих периодов.
Если по будущему периоду уже было отправлено напоминание со старой суммой, отметка сбрасывается:
бот пришлёт новое напоминание с правильной суммой. Просроченные и оплаченные периоды
сохраняют старую сумму — это уже выставленные счета.

**График** (`start_date`, `anchor_day`) — дату у существующего периода менять нельзя
(это правило ТЗ, его охраняет триггер в базе). Поэтому будущие неоплаченные периоды
удаляются и создаются заново по новому графику:

- Передали только `start_date` → ближайшая оплата будет в эту дату, а `anchor_day`
  станет днём из неё (`2026-11-10` → `anchor_day = 10`), как при создании платежа.
- Передали `start_date` и `anchor_day` → первая оплата в `start_date`, следующие — по `anchor_day`.
  Пример: `start_date = 2026-11-30`, `anchor_day = 31` → 30.11, 31.12, 31.01, 28.02, 31.03…
- Передали только `anchor_day` → ближайшая оплата — в том же месяце, где была прежняя
  ближайшая, но в новый день. Если этот день уже прошёл — в следующем месяце.
  В месяце, где уже есть оплаченный или прошедший период, второй период не создаётся.
- `start_date` должна быть **в месяце после последнего периода из истории**. Иначе — **409**,
  и в ответе будет указана дата последнего сохранённого периода. При ошибке не меняется ничего,
  даже если в том же запросе были другие поля.
- `start_date` в прошлом допустима, если истории нет (исправление ошибки при создании):
  создадутся прошедшие периоды, они будут просроченными.

Сумма и график вместе (`amount` + `anchor_day`) — новые периоды создаются сразу с новой суммой.

### Примеры запросов

Переименовать:
```json
{ "name": "Аренда офиса (БЦ Невский)" }
```

Повысить аренду со следующего счёта:
```json
{ "amount": 95000.00 }
```

Перевести подписку в евро:
```json
{ "amount": 110.00, "currency": "EUR" }
```

Перенести оплату на 10-е число каждого месяца:
```json
{ "anchor_day": 10 }
```

Перенести ближайшую оплату на конкретную дату:
```json
{ "start_date": "2026-11-10" }
```

Платить в последний день каждого месяца:
```json
{ "start_date": "2026-11-30", "anchor_day": 31 }
```

Напоминать за неделю:
```json
{ "remind_days_before": 7 }
```

### Ответ — 200 OK

Обычный объект платежа (как в `GET /api/v1/recurring-payments/{id}`) плюс четыре поля о том, что произошло:

```json
{
  "id": 1,
  "name": "Аренда офиса",
  "amount": "95000.00",
  "currency": "RUB",
  "periodicity": "monthly",
  "start_date": "2026-09-20",
  "anchor_day": 10,
  "remind_days_before": 3,
  "is_deleted": false,
  "deleted_at": null,
  "created_by": "admin",
  "created_at": "2026-09-01T12:00:00",
  "updated_at": "2026-10-24T16:30:00",
  "next_due_date": "2026-10-20",
  "periods_total": 3,
  "periods_unpaid": 2,

  "changed_fields": ["amount", "anchor_day"],
  "updated_periods": 0,
  "removed_periods": 1,
  "created_periods": 1
}
```

| Поле | Что значит |
|---|---|
| `changed_fields` | Какие поля реально изменились. Пустой список — новые значения совпали со старыми, ничего не сделано |
| `updated_periods` | Сколько будущих периодов получили новую сумму/валюту (без смены графика) |
| `removed_periods` | Сколько будущих неоплаченных периодов удалено при смене графика |
| `created_periods` | Сколько периодов создано по новому графику |

`next_due_date` — срок ближайшего **неоплаченного** периода. Если есть просроченный долг,
здесь будет его дата, а не новая.

### Ошибки

| Код | Когда | Пример `detail` |
|---|---|---|
| 401 | Не авторизован | `Требуется авторизация` |
| 403 | Не администратор | `Недостаточно прав: действие доступно только администратору` |
| 404 | Нет такого платежа | `Регулярный платёж не найден` |
| 409 | Платёж прекращён | `Прекращённый платёж изменить нельзя: его история хранится в неизменном виде` |
| 409 | `start_date` попадает в историю | `Новая дата ближайшей оплаты должна быть в месяце после последнего сохранённого периода (20.10.2026): …` |
| 422 | Пустое тело, `null`, неверный тип, сумма ≤ 0, валюта не из списка, `remind_days_before` < 3 и т. п. | Описание поля с ошибкой |

## 2. DELETE `/api/v1/recurring-payments/{payment_id}` — удалить платёж

Два режима.

### 2.1. Прекращение (по умолчанию, как требует ТЗ)

```
DELETE /api/v1/recurring-payments/1
```

Платёж помечается прекращённым: новые периоды не создаются, напоминания не отправляются.
Вся история оплат остаётся и видна в списках (`is_recurring_deleted: true`).
Прекращённый платёж скрыт из `GET /api/v1/recurring-payments`, но виден с `?include_deleted=true`.

### 2.2. Полное удаление

```
DELETE /api/v1/recurring-payments/1?permanent=true
```

Удаляет платёж **и все его периоды, включая оплаченные**. Восстановить нельзя.
Нужно, чтобы убрать платёж, созданный по ошибке. Работает и для уже прекращённого платежа.
Запись о удалении (название, сумма, валюта, сколько периодов удалено) остаётся в журнале
`GET /api/v1/audit-logs`.

Во фронтенде перед этим вызовом стоит показать подтверждение:
«Платёж и вся история его оплат будут удалены без возможности восстановления».

### Тело запроса

Не нужно.

### Ответ — 200 OK

Платёж в момент удаления плюс два поля:

```json
{
  "id": 1,
  "name": "Аренда офиса",
  "amount": "90000.00",
  "currency": "RUB",
  "...": "остальные поля платежа",
  "is_deleted": true,

  "permanent": false,
  "removed_periods": 0
}
```

| Поле | Что значит |
|---|---|
| `permanent` | `false` — прекращён, история сохранена; `true` — удалён полностью |
| `removed_periods` | Сколько периодов удалено. При прекращении всегда `0` |

При `permanent=true` объект — снимок до удаления: в нём `is_deleted` показывает
состояние на тот момент, а запрос `GET` по этому `id` после удаления вернёт **404**.

### Ошибки

| Код | Когда |
|---|---|
| 401 | Не авторизован |
| 403 | Не администратор |
| 404 | Нет такого платежа |
| 409 | Обычное прекращение уже прекращённого платежа: `Этот регулярный платёж уже прекращён` (полное удаление при этом работает) |

## 3. Журнал действий

Каждое изменение пишется в `audit_logs` — смотреть через `GET /api/v1/audit-logs`:

| `action_type` | Когда | Что в `details` |
|---|---|---|
| `UPDATE_RECURRING` | Изменение (только если что-то реально поменялось) | `changes: {поле: {old, new}}`, счётчики периодов |
| `DELETE_RECURRING` | Прекращение | название |
| `DELETE_RECURRING_PERMANENT` | Полное удаление | название, сумма, валюта, `removed_periods` |

---

## 4. Как это встроить во фронтенд

Форма редактирования:
1. `GET /api/v1/recurring-payments/{id}` — заполнить форму текущими значениями.
2. При сохранении отправить `PATCH` только с изменёнными полями (или всю форму — тоже работает).
3. Если `changed_fields` пуст — показать «Изменений нет».
4. Если `removed_periods` или `created_periods` > 0 — перезагрузить список периодов
   (`GET /api/v1/payment-occurrences?recurring_payment_id={id}`): их `id` изменились.
5. На 409 показать текст из `detail` — он написан для человека.

Кнопки удаления:
- «Прекратить» → `DELETE /api/v1/recurring-payments/{id}`
- «Удалить навсегда» → подтверждение → `DELETE /api/v1/recurring-payments/{id}?permanent=true`

Пример на JavaScript:
```js
const res = await fetch(`/api/v1/recurring-payments/${id}`, {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  credentials: "include",            // отправить cookie сессии
  body: JSON.stringify({ amount: 95000, anchor_day: 10 }),
});
const data = await res.json();
if (!res.ok) alert(typeof data.detail === "string" ? data.detail : "Проверьте поля формы");
```

У ошибки 422 `detail` — массив с описанием полей (стандартный формат FastAPI),
у остальных ошибок — строка.
